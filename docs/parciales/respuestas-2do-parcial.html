Pregunta 01 · CRÍTICA

Dibuja la arquitectura real de tu frontend y explica el recorrido entre sus carpetas.
Para entender el concepto

La arquitectura de un frontend es la forma en que repartes responsabilidades entre carpetas y archivos para que cada pieza haga una sola cosa. Piensa en un restaurante: el mozo (componente) toma el pedido, no cocina; la cocina (service) prepara, no atiende mesas; el proveedor (backend) entrega los ingredientes. Si el mozo también cocinara y fuera al mercado, cualquier cambio rompería todo.

La regla clave es la dirección de las dependencias: las pantallas usan hooks, los hooks usan services, los services usan el cliente HTTP, y el cliente HTTP usa la configuración. Nunca al revés: el cliente HTTP no sabe que existe una pantalla de productos.

Qué responder
  • El frontend de StockFlow es una SPA en React + TypeScript construida con Vite y organizada por features (capacidades de negocio), no por tipo de archivo.
  • Carpetas y responsabilidad:
    • app/: composición global (providers de tema, sesión demo y toasts), menú (navigation.ts) y ErrorBoundary.
    • routes/: qué página corresponde a cada URL (AppRouter.tsx).
    • layouts/: la estructura que no cambia entre pantallas (Sidebar + Header + Outlet).
    • pages/ y features/*/pages/: cada pantalla compone componentes y decide qué hacer.
    • features/<modulo>/: todo lo de un módulo de negocio junto (models, types, services, hooks, components, pages, utils).
    • components/ui/: piezas visuales genéricas sin lógica de negocio (Button, Modal, Pagination…). components/common/: piezas del "marco" (Sidebar, Header).
    • api/: la única puerta HTTP (apiFetch) y la traducción de errores.
    • config/: lectura de variables de entorno. shared/: hooks y utilidades genéricas. styles/: design tokens y CSS.
  • Organización física vs responsabilidad: la carpeta es dónde vive el archivo; la responsabilidad es qué decide. ProductoForm vive en features/productos/components porque pertenece al negocio de productos; Button vive en components/ui porque no sabe nada de productos.
  • Dirección del flujo: ProductosPage → useProductos → productoService → apiFetch → config/env. Los componentes UI no importan nada de features/; la tabla no importa services. Así se evita que "cualquier componente llame a cualquier cosa".
Muéstralo en el código
  • Árbol de src/ en WebStorm: app, routes, layouts, pages, features, components/ui, components/common, api, config, shared, styles, test.
  • Cadena real: src/features/productos/pages/ProductosPage.tsx:42 (useProductos()) → features/productos/hooks/useProductos.ts:5 → features/productos/services/productoService.ts:6-9 → src/api/apiClient.ts:52-68 → src/config/env.ts:2.
  • La tabla no importa services: features/productos/components/ProductoTable.tsx:1-12 (sólo UI, modelos y utilidades).
Si muevo toda la lógica HTTP dentro de un componente visual, ¿el proyecto puede funcionar? Aunque funcione, ¿qué problema de acoplamiento aparece?
Sí, puede funcionar: fetch se puede llamar desde cualquier componente. Pero el componente quedaría acoplado a la URL, a los headers, al formato de errores y al backend: no se podría reutilizar con otros datos, habría que repetir la verificación de response.ok en cada pantalla, probarlo exigiría simular fetch en cada test y un cambio de URL o de librería (por ejemplo pasar a Axios) obligaría a editar todas las pantallas. Con apiClient + services ese cambio se hace en un solo lugar.

Pregunta 02

Explica qué problema resuelve Vite y qué ocurre en npm install, npm run dev y npm run build.
Para entender el concepto

El navegador sólo entiende HTML, CSS y JavaScript. Nosotros escribimos TypeScript y JSX (TSX), importamos librerías de node_modules y CSS desde archivos de código. Alguien tiene que traducir todo eso: esa es la tarea de una build tool.

Hay tres herramientas distintas que conviene no confundir: npm es el gestor de paquetes (descarga librerías), Vite en modo dev es un servidor de desarrollo que traduce los archivos al vuelo y recarga sólo lo que cambió (HMR), y Vite build es el empaquetador que genera los archivos finales optimizados para producción.

Qué responder
  • Vite resuelve dos problemas: en desarrollo, levantar la app al instante y reflejar cada cambio sin recargar toda la página; en producción, generar un paquete pequeño y optimizado.
  • npm install: el gestor de paquetes lee package.json (qué librerías y rangos de versión) y package-lock.json (las versiones exactas) y descarga todo a node_modules/. No compila nada.
  • npm run dev → vite: levanta el servidor de desarrollo en http://localhost:5173. Transforma cada .ts/.tsx a JavaScript cuando el navegador lo pide y aplica HMR (Hot Module Replacement): al guardar un archivo sólo se reemplaza ese módulo y el estado de la pantalla suele conservarse.
  • npm run build → tsc -b && vite build: primero tsc verifica los tipos (si hay un error de TypeScript el build se detiene); luego Vite empaqueta: une módulos, elimina código no usado, minifica, separa en trozos (code splitting) y deja todo en dist/.
  • Vite no reemplaza a React ni a TypeScript: React dibuja la interfaz, TypeScript define y verifica tipos, Vite sólo transforma y sirve/empaqueta los archivos.
  • En StockFlow el servidor de desarrollo está fijado en el puerto 5173 con strictPort: true: si el puerto está ocupado, Vite se detiene con un error claro en vez de usar 5174 (que el CORS del backend no permite).
Muéstralo en el código
  • package.json → "scripts": dev, build, lint, preview, test, test:run.
  • vite.config.ts:5-12: plugin de React y server.port: 5173 + strictPort.
  • package-lock.json (versiones exactas) y node_modules/ (ignorado por Git).
Demuéstralo
Con npm run dev abierto, cambia un texto de pages/InicioPage.tsx y guarda: la pantalla se actualiza sin recargar (HMR). Luego ejecuta npm run build y muestra la carpeta dist/assets con varios archivos .js (uno por página lazy).
Si eliminas node_modules pero conservas package.json y package-lock.json, ¿cómo recuperas el proyecto y por qué?
Con npm install (o npm ci, que instala exactamente lo del lock y falla si no coincide). node_modules es un resultado reproducible: package.json dice qué dependencias hacen falta y package-lock.json fija las versiones exactas, así que se reconstruye idéntico. Por eso node_modules no se sube a Git.

Pregunta 03

Explica el arranque real del frontend: index.html → main.tsx → App.tsx → Router → pantalla.
Para entender el concepto

Una SPA empieza con un HTML casi vacío: sólo un <div id="root"> y un <script>. Todo lo que ves después lo construye React con JavaScript. El HTML es el "terreno vacío"; React es el que levanta la casa dentro de ese terreno.

Qué responder
  1. index.html se descarga primero. Tiene <div id="root"></div> y <script type="module" src="/src/main.tsx">. (StockFlow además aplica el tema claro/oscuro antes del primer pintado para evitar un destello.)
  2. main.tsx busca ese div con document.getElementById('root'), crea la raíz de React con createRoot(...) y llama a .render(...) con el árbol inicial: StrictMode → AppErrorBoundary → BrowserRouter → App. Aquí también se importan los CSS globales y la fuente.
  3. App.tsx sólo envuelve con los providers globales (tema, sesión demo, toasts) y delega en AppRouter.
  4. AppRouter compara la URL con sus <Route> y elige qué renderizar: para /productos, el layout MainLayout y dentro de su Outlet, ProductosPage.
  5. ProductosPage se monta, su hook dispara la petición al backend y la pantalla se completa cuando llegan los datos.

HTML base vs UI dinámica: lo que está en index.html existe antes de React; todo lo demás (menú, tablas, formularios) lo crea React dentro de #root y lo actualiza sin recargar la página.

Muéstralo en el código
  • index.html:21-22: <div id="root"> y el script de /src/main.tsx.
  • src/main.tsx:15-23: createRoot(document.getElementById('root')!).render(...).
  • src/app/App.tsx:6-16: providers y <AppRouter />.
  • src/routes/AppRouter.tsx:39-52: rutas hijas del layout.
Si main.tsx apunta a un id que no existe en index.html, ¿qué esperas que ocurra?
getElementById devuelve null. El ! de TypeScript sólo silencia el aviso en compilación, no evita el problema: en ejecución createRoot(null) lanza un error ("Target container is not a DOM element"), la app no se monta y la página queda en blanco con el error en la consola. Ni siquiera el ErrorBoundary puede mostrarse, porque React nunca llegó a renderizar.

Pregunta 04

Diferencia interface, type y los tipos reales en tiempo de ejecución usando Cliente y Vehículo (en StockFlow: Categoría y Producto).
Para entender el concepto

TypeScript es como un corrector ortográfico: revisa tu código mientras escribes y al compilar, pero cuando el programa se ejecuta en el navegador ya no está. Al compilar, todos los tipos se borran y queda JavaScript puro.

interface y type sirven para describir la forma de los datos. interface describe objetos y se puede extender; type es más general: además de objetos puede expresar uniones ('A' | 'B'), tipos derivados de otros y combinaciones. Ninguno de los dos crea objetos ni valida nada en tiempo de ejecución.

Qué responder
  • TypeScript verifica en desarrollo y compilación. Sus tipos no existen en runtime: no hay ningún objeto Producto que valide el JSON que llega del backend.
  • Uso interface para formas de objetos: Producto, Categoria, ProductoFormData, ProductoCreateRequest. ProductoUpdateRequest extiende la de creación y agrega activo.
  • Uso type cuando necesito algo que una interface no expresa bien: la unión de unidades de medida derivada de una constante (type UnidadMedida = (typeof UNIDADES_MEDIDA)[number]) o el tipo de errores del formulario (Partial<Record<keyof ProductoFormData, string>>).
  • Hay tres tipos por entidad, cada uno con un propósito: el modelo de la respuesta (Producto), el estado del formulario (ProductoFormData, todo texto) y el payload que se envía (ProductoCreateRequest/UpdateRequest, ya con números).
  • El proyecto usa TypeScript 6, que trae strict activado por defecto: por eso descripcion: string | null obliga a tratar el null antes de usarlo.
  • Ni interface ni type "crean" objetos: los objetos se crean con literales {...} o llegan del JSON.parse de la respuesta.
Muéstralo en el código
  • src/features/productos/models/Producto.ts:2-3 (as const + type UnidadMedida) y :19-29 (interface Producto).
  • src/features/productos/types/ProductoFormData.ts:7-16 y types/ProductoRequests.ts:4-17 (extends).
  • src/features/productos/utils/productoValidation.ts:4 (type ProductoFormErrors).
  • src/api/apiClient.ts:67: (await response.json()) as T — el as sólo "confía", no comprueba.
Si el backend envía un JSON con un campo faltante, ¿TypeScript lo bloquea automáticamente en runtime? ¿Por qué?
No. Los tipos se borran al compilar y apiFetch hace response.json() as T, que es una afirmación, no una validación. Si falta nombre, el objeto llega igual y en pantalla aparecerá undefined o se romperá un .toLowerCase(). Para validar en runtime haría falta código explícito (comprobaciones manuales o una librería de esquemas como Zod). Por eso el contrato con el backend debe mantenerse sincronizado y probarse.

Pregunta 05 · CRÍTICA

¿Por qué el frontend no debe copiar ciegamente las @Entity JPA del backend? Defiende tus contratos TypeScript.
Para entender el concepto

Hay tres "versiones" de un mismo dato y cada una sirve a un público distinto:

  • Modelo de persistencia (entidad JPA): cómo se guarda en la base. Tiene detalles internos (fechas de auditoría, relaciones como objetos completos).

Pregunta 22

¿Por qué fetch() no considera automáticamente un 404 o 500 como rechazo de la Promise?
Para entender el concepto

Para fetch, "funcionó" significa "recibí una respuesta del servidor", sin importar si es buena o mala. Un 404 o un 500 son respuestas completas y válidas desde el punto de vista de la red. fetch sólo rechaza la Promise cuando no hubo respuesta: sin conexión, servidor apagado, CORS bloqueado, URL imposible o petición abortada.

    • Error HTTP → ApiError con status (400, 404, 409, 422, 500).
    • Error de red → TypeError → mensajeDeError dice "No se pudo conectar con el backend. ¿Está corriendo StockFlowApplication en el puerto 8080?".
    • Aborto → AbortError, que se ignora (no es un error del sistema).
  • Las Pages y formularios no revisan status: reciben un error ya clasificado y lo traducen con describirError.

Pregunta 23 · CRÍTICA

¿Qué es CORS y por qué Postman/Swagger pueden funcionar mientras React falla en el navegador?
Para entender el concepto

Por seguridad, el navegador no deja que una página lea respuestas de otro origen (otro dominio, puerto o protocolo) salvo que ese otro servidor diga explícitamente "este origen tiene permiso". Esa regla del navegador se llama CORS (Cross-Origin Resource Sharing).

Origen = esquema + host + puerto. http://localhost:5173 y http://localhost:8080 comparten esquema y host, pero no puerto: son orígenes distintos. Postman no es un navegador y no aplica CORS. Swagger UI se sirve desde el mismo backend (puerto 8080), así que sus peticiones son del mismo origen.

Qué responder
  • CORS es una política del navegador, no del backend ni de la base. El servidor sólo declara a quién permite; quien bloquea es el navegador.
  • React corre en http://localhost:5173 y la API en http://localhost:8080: orígenes distintos. El navegador envía el header Origin y sólo entrega la respuesta a JavaScript si vuelve Access-Control-Allow-Origin con ese origen.
  • En POST, PUT y DELETE con Content-Type: application/json, el navegador manda antes una petición preflight (OPTIONS) preguntando si el método y los headers están permitidos.
  • En StockFlow, CorsConfig permite en /api/** los orígenes de stockflow.cors.allowed-origins (por defecto http://localhost:5173, configurable con CORS_ALLOWED_ORIGINS), los métodos GET, POST, PUT, DELETE y OPTIONS, los headers Content-Type y Accept, y expone Location. Por eso Vite tiene strictPort: true: si arrancara en 5174, CORS fallaría.
  • Cómo se diagnostica: la consola muestra "blocked by CORS policy"; en Network la petición aparece en rojo o con "CORS error", a veces con un OPTIONS previo fallido; y en JavaScript llega como TypeError (por eso el mensaje "No se pudo conectar con el backend").

Pregunta 38 · CRÍTICA

Para entender el concepto

Renderizar debe ser un cálculo puro: con las mismas props y estado, el mismo resultado. Pero a veces el componente tiene que mantenerse en sintonía con algo fuera de React: un servidor, un temporizador, el foco del navegador, un <dialog> nativo. Para eso existe useEffect.

Pregunta 39 · CRÍTICA

Explica cleanup, AbortController y cómo evitas respuestas obsoletas/race conditions.
Para entender el concepto

Las respuestas de red no llegan necesariamente en el orden en que se pidieron. Si pides la página 1 y enseguida la página 2, y la 1 tarda más, la respuesta vieja puede llegar después y pisar a la nueva: es una condición de carrera (race condition).

AbortController es una API del navegador para cancelar un fetch: creas un controlador, pasas su signal a fetch y, cuando llamas a controller.abort(), esa petición se cancela y su Promise se rechaza con un AbortError.

Qué responder
  • Crear y pasar la señal: useAsyncList crea new AbortController() en cada ejecución del Effect y pasa controller.signal al loader → service → apiFetch → fetch.
  • Abortar en el cleanup: return () => controller.abort(). Se ejecuta al desmontar la pantalla o antes de repetir el Effect (por ejemplo, con reload()).
  • AbortError no es un error funcional: isAbortError(err) lo reconoce (DOMException con name === 'AbortError') y no se muestra mensaje. Además setLoading(false) sólo se ejecuta si la señal no fue abortada, para no apagar el indicador de una petición más nueva.
  • El mejor ejemplo es useKardex: cada combinación producto/página/tamaño genera una key; el Effect aborta la petición anterior y además guarda cada resultado junto con la key que lo produjo. Sólo se muestra el resultado cuya key coincide con la actual; "cargando" se deriva (la key actual todavía no tiene resultado). Así una respuesta lenta de la página 1 nunca pisa a la de la página 2.
Muéstralo en el código

  • src/shared/utils/isAbortError.ts:2-4.
  • src/features/inventario/hooks/useKardex.ts:9-48 (comentario y lógica con key).

Demuéstralo

Si buscas A y enseguida B, pero la respuesta de A llega después, ¿cómo evitas mostrar A como si fuera el resultado actual?
De dos formas que StockFlow combina en useKardex: 1) cancelar la petición de A en el cleanup cuando cambia el parámetro a B (controller.abort()), así su respuesta nunca se procesa; 2) etiquetar cada resultado con la key de la petición que lo produjo y mostrar sólo el que coincide con la key actual. Aunque A llegara igual (por ejemplo, porque el servidor ya había respondido), se descarta porque su key no es la de B.

Pregunta 46

Diferencia ErrorBoundary de manejo de errores de fetch.
Para entender el concepto

Un ErrorBoundary es una "red de seguridad" para errores que ocurren mientras React dibuja la pantalla (por ejemplo, leer una propiedad de undefined en el JSX). Si un componente explota al renderizar, el boundary muestra una pantalla alternativa en vez de dejar todo en blanco.

Pero no ve los errores que ocurren fuera del render: los de un fetch (son asíncronos) ni los de un handler de clic. Esos se manejan con try/catch y se convierten en estado (un mensaje en pantalla).

Qué responder
  • AppErrorBoundary es un componente de clase (los boundaries todavía requieren getDerivedStateFromError y componentDidCatch). Envuelve toda la app en main.tsx; si un render falla, muestra "La interfaz tuvo un problema" con role="alert" y registra el error en consola.
  • Los errores HTTP son esperables y se representan como estado controlado: apiFetch lanza ApiError, el hook o el formulario lo captura y la pantalla muestra un Alert o un toast con opción de reintentar. La app sigue funcionando.
  • El boundary no es un sistema universal de excepciones: si lo usara para errores de red, un 409 haría desaparecer toda la pantalla en lugar de mostrar "código repetido" junto al campo.
Muéstralo en el código
  • src/app/AppErrorBoundary.tsx:6-31 (el comentario aclara: "NO captura errores de fetch ni de event handlers").
  • src/main.tsx:17 (dónde envuelve).
  • Errores de fetch como estado: src/shared/hooks/useAsyncList.ts:28-29 y features/productos/components/ProductoForm.tsx:114-121.
Si fetch responde 500 y tu service lo convierte en Error controlado, ¿por qué no deberías depender sólo de ErrorBoundary?
Porque el error ocurre en código asíncrono (dentro de un Effect o de un handler), fuera del render, y el boundary no lo ve: la promesa rechazada quedaría sin manejar y la pantalla seguiría "cargando" para siempre. Y aunque se forzara a llegar al boundary, se perdería toda la pantalla por un error recuperable. Lo correcto es try/catch → estado de error → mensaje con "Reintentar", como hace StockFlow.

Pregunta 48

BrowserRouter en producción: explica fallback SPA, rutas directas y CORS productivo.
Para entender el concepto

En una SPA sólo existe un archivo HTML real: index.html. Rutas como /productos las inventa React Router en el navegador. Si el usuario entra directo a https://midominio.com/productos (o recarga ahí), el navegador le pide al servidor web un archivo /productos que no existe → 404. El fallback SPA es una regla del servidor: "si no encuentras el archivo, devuelve index.html"; React arranca, lee la URL y muestra la pantalla correcta.

Qué responder
  • Con BrowserRouter las URLs son "limpias" (/productos), así que el hosting debe tener fallback a index.html para cualquier ruta que no sea un archivo de assets/. En desarrollo Vite ya lo hace solo; en producción lo configura quien sirve dist/: 
    nginx:   location / { try_files $uri $uri/ /index.html; }
Netlify: archivo public/_redirects →  /*  /index.html  200
Vercel:  vercel.json → { "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }
  • CORS productivo: el backend debe permitir el origen real del frontend (por ejemplo https://stockflow.miempresa.com) con la variable CORS_ALLOWED_ORIGINS; nunca * por comodidad.
  • Dos 404 distintos: el 404 del hosting (no hay fallback: se pidió un documento HTML para /productos) y el 404 de la API (un endpoint o recurso inexistente en /api/..., que llega como JSON y lo muestra la app). En Network el primero es de tipo document y el segundo fetch.
  • La pantalla de StockFlow para rutas inexistentes dentro de la app (NotFoundPage, path="*") sólo funciona si el servidor primero entrega index.html.
Muéstralo en el código
  • src/main.tsx:18 (BrowserRouter) y src/routes/AppRouter.tsx:51 (path="*").
  • Backend: application.yml → stockflow.cors.allowed-origins: ${CORS_ALLOWED_ORIGINS:http://localhost:5173}.
  • Pendiente: StockFlow todavía no incluye la configuración del fallback para un hosting concreto (ver la sección de pendientes).
Si / funciona pero al refrescar /vehiculos (/productos) el servidor devuelve 404, ¿qué configuración falta probablemente?
El fallback SPA del servidor web: la regla que devuelve index.html para rutas que no son archivos (try_files ... /index.html en nginx, rewrites en Vercel, _redirects en Netlify). / funciona porque ahí sí existe index.html; /productos no existe como archivo. No es un problema de React Router ni del backend.

Glosario de términos técnicos

Cada término está explicado de forma simple y relacionado con StockFlow. Entre corchetes, las preguntas donde aparece.

A
AbortController / AbortSignal
API del navegador para cancelar operaciones asíncronas como fetch. Se crea un AbortController, se pasa su signal a fetch y, al llamar controller.abort(), la petición se corta y su Promise se rechaza con un AbortError. En StockFlow se usa en el cleanup de useAsyncList y useKardex para que una pantalla cerrada o una petición vieja no actualicen el estado. [39, 38, 40]
AbortError
El error que produce una petición cancelada. No es un fallo del sistema (fue intencional), por eso isAbortError() lo reconoce y no se muestra ningún mensaje. [39, 22]
Accesibilidad (a11y)
Que la aplicación pueda usarla cualquier persona: con teclado, con lector de pantalla, con baja visión. Se logra con etiquetas (label), roles, atributos aria-*, foco bien manejado, botones reales y buen contraste. "a11y" es la abreviatura en inglés (a + 11 letras + y). [20, 42, 44]
Adapter (adaptador)
Pieza que traduce entre dos formatos para que el resto del código no dependa del exterior. En el frontend sería la función que convierte la respuesta del backend al modelo de la UI; si el backend renombra un campo, sólo se toca el adapter. [05]
API / API REST
API (interfaz de programación) es el conjunto de operaciones que un sistema ofrece a otros. Una API REST las ofrece por HTTP usando recursos con URL (/api/productos) y métodos (GET, POST, PUT, DELETE). El backend de StockFlow es una API REST que el frontend consume. [06, 21]
apiClient / apiFetch
El módulo src/api/apiClient.ts: la única puerta HTTP del frontend. Agrega la URL base y los headers JSON, llama a fetch, revisa response.ok, convierte errores en ApiError y trata el 204. [21, 22, 24]
ApiError
Clase de error propia de StockFlow (extiende Error) que lleva el status HTTP y los fieldErrors enviados por el backend. Permite que las pantallas distingan un 404 de un 409 sin leer la respuesta. [22, 29]
aria-* (atributos ARIA)
Atributos HTML que describen elementos a los lectores de pantalla: aria-label (nombre), aria-labelledby/aria-describedby (enlazan con un título o una ayuda), aria-invalid (campo con error), aria-current (página actual), aria-busy (cargando), aria-hidden (decorativo). [20, 42]
async / await
async marca una función que devuelve una Promise. Dentro de ella, await espera el resultado de otra Promise sin bloquear el navegador: la función queda en pausa y el resto de la página sigue funcionando. [31]
Asíncrono
Una operación que termina "más tarde" (una petición de red, un temporizador). El programa no se queda esperando: sigue con otras cosas y procesa el resultado cuando llega. [31, 38]
B
Backend
La parte del sistema que corre en el servidor: reglas de negocio, acceso a la base de datos y API. En StockFlow es Spring Boot (Java 21) con PostgreSQL. El frontend nunca habla con la base directamente: siempre pasa por el backend. [21, 50]
Batching
React agrupa varias actualizaciones de estado que ocurren juntas (por ejemplo setData y setLoading) en un solo re-render, para no dibujar la pantalla varias veces. [21]
Bean Validation (@Valid)
Mecanismo del backend Java que valida los datos de entrada con anotaciones (@NotBlank, @Size…). Si fallan, el backend responde 400 con los errores por campo. [14, 29]
Body (cuerpo)
El contenido de una petición o respuesta HTTP. En StockFlow es JSON. GET y DELETE normalmente no llevan body; POST y PUT sí. Una respuesta 204 no tiene body. [21, 25, 28]
BrowserRouter
Componente de React Router que usa la History API del navegador para manejar URLs "limpias" (/productos). Requiere fallback SPA en producción. [06, 48]
Build
El proceso que transforma el código fuente en los archivos finales que se publican. En StockFlow, npm run build verifica los tipos con tsc y empaqueta con Vite en dist/. [02, 47]
Bundle / bundler
Un bundle es un archivo JavaScript que junta muchos módulos. El bundler (Vite usa Rollup/Rolldown en el build) los une, elimina lo que no se usa y los minifica para que el navegador descargue menos. [02, 47]
C
Caché y hash en nombres
El navegador guarda archivos para no descargarlos de nuevo. Vite agrega un hash al nombre (apiClient-VTyo5whh.js) que cambia cuando cambia el contenido; así una versión nueva nunca se confunde con una vieja guardada. [47]
Callback
Una función que se pasa a otro componente o función para que la "llame de vuelta" cuando ocurra algo. En React, los callbacks por props (onEdit, onSaved, onConfirm) permiten que un hijo avise al padre. [10, 15]
Cleanup
La función que devuelve un useEffect. React la ejecuta antes de repetir el Effect y al desmontar el componente, para deshacer lo que hizo el setup (cancelar peticiones, temporizadores o suscripciones). [38, 39, 40]
Code splitting / lazy loading
Dividir el JavaScript en trozos y descargar cada uno sólo cuando hace falta. StockFlow usa lazy(() => import(...)) en las páginas: el código de Productos se descarga la primera vez que se visita. Mientras llega, Suspense muestra un esqueleto. [02, 06]
Código de estado HTTP (status)
Número que indica el resultado de una petición. 2xx = éxito (200 OK, 201 Created, 204 No Content); 4xx = error del cliente (400 datos inválidos, 404 no existe, 409 conflicto, 422 regla de negocio); 5xx = error del servidor (500). [22, 29]
Componente
Función de React que recibe props y devuelve la interfaz (JSX). Es la pieza básica de la UI: Button, ProductoTable, ProductosPage. [08, 10]
Componente (input) controlado
Un control de formulario cuyo valor sale del estado de React (value) y se actualiza con onChange. El estado es la fuente de verdad, no el DOM. El opuesto es el no controlado, que guarda su propio valor (defaultValue). [11, 34]
Constraint (restricción)
Regla que la base de datos hace cumplir siempre: PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK, NOT NULL. Es la última línea de defensa de la integridad. [14, 33]
Contrato (HTTP)
El acuerdo entre frontend y backend: qué URL, método, campos, tipos, status y formato de error tiene cada operación. Los modelos TypeScript del frontend reflejan ese contrato (los DTO), no la base de datos. [05, 43, 45]
Context (React)
Mecanismo para compartir un valor con muchos componentes sin pasarlo por props en cada nivel. StockFlow lo usa para el tema, la sesión demo y los toasts (los providers de App.tsx). [03, 41]
CORS (Cross-Origin Resource Sharing)
Regla de seguridad del navegador: una página sólo puede leer respuestas de otro origen si ese servidor lo autoriza con la cabecera Access-Control-Allow-Origin. Postman no la aplica porque no es un navegador. [23, 32, 48]
CRUD
Las cuatro operaciones básicas sobre datos: Create (POST), Read (GET), Update (PUT) y Delete (DELETE). [25-28]
D
Design tokens
Variables CSS con nombres de significado (--surface, --text-muted, --brand) en lugar de colores o medidas sueltas. Todos los componentes las usan, así el diseño es coherente y el tema oscuro se logra cambiando sólo los valores. En StockFlow: styles/tokens.css. [42]
DevTools (Network, Console)
Herramientas del navegador (F12). Network muestra cada petición real (URL, método, status, headers, payload, respuesta, tiempo); Console muestra errores y avisos. Son la evidencia para diagnosticar. [21, 32, 50]
dist/
Carpeta que genera npm run build: index.html y assets/ con el JavaScript y CSS finales. Es lo que se sube al hosting. No se versiona en Git. [47]
DOM
(Document Object Model) La representación en memoria de la página que el navegador muestra. React calcula qué debe cambiar y actualiza el DOM por nosotros. [03, 11]
DTO (Data Transfer Object)
Objeto pensado sólo para transportar datos entre sistemas (por ejemplo ProductoResponse o CrearProductoRequest del backend). Define la forma del JSON, separada de cómo se guarda en la base. [05, 35]
E
Effect / useEffect
Hook para sincronizar un componente con algo externo a React (API, temporizador, foco, <dialog>). Tiene setup, dependencias y cleanup. Se ejecuta después del render cuando cambian sus dependencias. [38, 39, 40]
Endpoint
Una dirección concreta de la API con un método: GET /api/productos, PUT /api/productos/{id}. No confundir con una ruta del navegador. [06, 32]
Entidad JPA (@Entity)
Clase del backend que representa una tabla de la base de datos (ProductoJpaEntity). Es un detalle interno del backend; el frontend no debe copiarla. [05]
Error Boundary
Componente que atrapa errores ocurridos durante el render de sus hijos y muestra una pantalla alternativa. No atrapa errores de fetch ni de handlers de eventos. En StockFlow: AppErrorBoundary. [46]
Error de red
Cuando la petición no obtiene ninguna respuesta (servidor apagado, sin conexión, CORS bloqueado). fetch lanza TypeError. Es distinto de un error HTTP, que sí trae status. [22, 23]
Estado (state)
Datos que pertenecen a un componente y que, al cambiar, hacen que React vuelva a dibujarlo. Se crea con useState y sólo se cambia con su setter. [10, 11, 17]
Estado fuente / estado derivado
Fuente: lo mínimo que hay que guardar (datos del backend, lo que eligió el usuario). Derivado: lo que se calcula a partir de la fuente (lista filtrada, página, totales). Lo derivado no se guarda en useState para que nunca quede desincronizado. [17, 19, 49]
Event loop
El mecanismo del navegador que procesa tareas una por una (eventos, respuestas de red, renders). Gracias a él un await no congela la página: mientras se espera, se atienden otras tareas. [31]
Evento / evento tipado
Aviso que genera el navegador cuando el usuario interactúa (clic, tecla, envío). En TypeScript se tipa: ChangeEvent<HTMLInputElement>, FormEvent<HTMLFormElement>. [13]
F
Fallback SPA
Regla del servidor web que devuelve index.html para cualquier ruta que no sea un archivo real, para que React Router pueda resolver URLs como /productos al entrar directo o al recargar. [48]
Feature (carpeta)
Forma de organizar el código por capacidad de negocio: todo lo de productos (modelos, service, hooks, componentes, páginas) vive en features/productos/. [01, 08]
fetch
Función del navegador para hacer peticiones HTTP. Devuelve una Promise con un Response. Sólo rechaza ante errores de red o aborto; un 404 o un 500 "resuelven" igual. [21, 22]
fieldErrors
Objeto que envía el backend en un 400 con el error de cada campo ({ codigo: "no debe estar vacío" }). El formulario lo usa para mostrar cada mensaje junto a su input. [14, 22, 25]
FK (clave foránea)
Columna que apunta a la clave primaria de otra tabla y que la base obliga a ser válida. producto.categoria_id es la FK hacia categoria: materializa la relación 1:N. [33, 35]
FormData (en StockFlow)
Tipo del estado de un formulario (ProductoFormData): representa los datos mientras se editan, con números como texto. No confundir con la clase FormData del navegador, que StockFlow no usa. [05, 12]
Frontend
La parte del sistema que ve y usa la persona: corre en el navegador. En StockFlow, React + TypeScript + Vite. [01]
G - H
Genérico (<T>)
Un "tipo comodín" que se completa al usarlo. useAsyncList<T> funciona para cualquier entidad: con T = Producto devuelve Producto[]. Evita escribir lo mismo para cada tipo. [41]
Header (cabecera HTTP)
Información extra de una petición o respuesta: Content-Type (formato del body), Accept (formato que acepto), Origin (desde dónde se pide), Location (URL del recurso creado). [21, 23, 25]
HMR (Hot Module Replacement)
Función del servidor de desarrollo de Vite: al guardar un archivo, reemplaza sólo ese módulo en el navegador sin recargar la página, conservando casi siempre el estado. [02]
Hook
Función de React que empieza con use y da capacidades a un componente: useState (estado), useEffect (sincronización), useMemo (memorizar cálculos), useId (ids únicos), useCallback (funciones estables). Sólo se llaman en el nivel superior de un componente o de otro hook. [11, 38, 41]
Hook personalizado (custom hook)
Función propia que agrupa hooks para reutilizar lógica: useAsyncList, useProductos, useKardex. Comparte la lógica, no el estado: cada llamada tiene el suyo. [41]
Hosting
El servidor o servicio donde se publica la aplicación (nginx, Vercel, Netlify…). Para un frontend Vite basta con servir los archivos de dist/ con fallback SPA. [47, 48]
HTTP y sus métodos
Protocolo de petición/respuesta de la web. Métodos: GET (leer), POST (crear), PUT (reemplazar), DELETE (borrar), OPTIONS (preguntar qué se permite; lo usa el preflight de CORS). [21-28]
I - J - K
Idempotencia
Una operación es idempotente si repetirla deja el mismo resultado que hacerla una vez. PUT y DELETE lo son; POST no (dos POST crean dos registros o el segundo da 409). [27]
import.meta.env
Objeto donde Vite expone las variables de entorno al código. Sólo incluye las que empiezan con VITE_ (más algunas propias como MODE). Su valor se incrusta al compilar. [09, 47]
Inmutabilidad
No modificar un objeto o array existente, sino crear uno nuevo con el cambio ({ ...prev, campo }, [...prev, nuevo], map, filter). React detecta cambios comparando referencias; si mutas, puede no re-renderizar. [11, 16, 25]
Integración (prueba de)
Prueba que verifica que varias piezas reales funcionan juntas, por ejemplo el frontend contra el backend real. Detecta errores de contrato que los mocks no ven. [43, 45]
interface / type
Formas de declarar tipos en TypeScript. interface describe la forma de un objeto y se puede extender (extends); type además permite uniones, tipos derivados y combinaciones. Ambos desaparecen al compilar. [04]
Inversión de control
En vez de que un componente decida todo, recibe desde afuera qué hacer (callbacks). La tabla emite "quieren editar"; la página decide el efecto. [15]
jsdom
Implementación de un navegador en JavaScript, sin pantalla, que usa Vitest para que existan document y window en las pruebas. No implementa todo (por ejemplo <dialog>.showModal()), por eso test/setup.ts lo simula. [44]
JSON
Formato de texto para datos ({"id": 1, "nombre": "Resma"}). Viaja en el body de las peticiones; JSON.stringify convierte objetos a texto y response.json() hace lo contrario. [21, 25]
JSX / TSX
Sintaxis que permite escribir algo parecido a HTML dentro de JavaScript (<Button>Guardar</Button>). TSX es lo mismo en archivos TypeScript. Vite la transforma en llamadas de JavaScript. [02, 03]
Kardex
Registro histórico de todos los movimientos de inventario de un producto (entradas, salidas, transferencias) con el saldo resultante. En StockFlow se consulta paginado en el servidor desde la pantalla Movimientos. [37, 39]
key
Identificador único que React usa para reconocer cada elemento de una lista entre renders. Debe ser estable (el id), no el índice. [16]
L - M
Layout
Estructura fija que envuelve varias páginas (menú, encabezado). En StockFlow, MainLayout, con un Outlet donde se pinta la página actual. [06, 08]
Link / NavLink
Componentes de React Router para navegar sin recargar. NavLink además sabe si su ruta está activa (isActive) para resaltarla en el menú. [07]
Linter
Herramienta que revisa el código buscando errores y malas prácticas sin ejecutarlo. StockFlow usa oxlint (npm run lint), con reglas de hooks de React. [38]
Map
Estructura de JavaScript que guarda pares clave → valor y busca por clave al instante. categoriasPorId es un Map<number, Categoria>. [36]
map / filter / find
Métodos de arrays. map transforma cada elemento; filter se queda con los que cumplen una condición; find devuelve el primero que la cumple. Ninguno modifica el array original. [16]
Minificar
Reducir el tamaño del código quitando espacios, comentarios y acortando nombres, sin cambiar lo que hace. Lo hace el build. [02, 47]
Mock
Reemplazo falso de una dependencia en una prueba, que responde lo que el test decide. StockFlow simula los services con vi.mock y fetch con vi.stubGlobal. [43, 45]
Modal / <dialog>
Ventana que aparece encima de la página y bloquea el fondo hasta cerrarse. StockFlow usa el elemento nativo <dialog> con showModal(), que ya maneja foco, Escape y fondo inerte. [20, 42]
Modo (development / production / test)
Vite carga un archivo .env distinto según el modo: npm run dev → development, npm run build → production, Vitest → test. [09, 47]
MSW (Mock Service Worker)
Librería que intercepta las peticiones a nivel de red durante las pruebas y responde datos simulados. Permite probar también el cliente HTTP y las URLs. StockFlow no la usa. [45]
N - O
node_modules / package.json / package-lock.json
package.json lista las dependencias y los scripts; package-lock.json fija las versiones exactas instaladas; node_modules/ contiene las librerías descargadas (se regenera con npm install y no se sube a Git). [02]
npm
El gestor de paquetes de Node.js: instala librerías (npm install) y ejecuta los scripts de package.json (npm run dev). [02]
Origen (origin)
La combinación de esquema + host + puerto de una URL. http://localhost:5173 y http://localhost:8080 son orígenes distintos porque cambia el puerto. [23]
Outlet
Componente de React Router que marca el lugar dentro de un layout donde se pinta la ruta hija que coincide con la URL. [06]
P
Page (página)
Componente que representa una pantalla completa y coordina su lógica: carga datos, maneja estado y decide qué hacer en cada acción (ProductosPage). [08, 10]
Paginación (cliente / servidor)
Dividir una lista en páginas. En el cliente: se descargan todos los datos y se cortan con slice (Productos). En el servidor: se pide sólo una página y el backend informa el total (Kardex). [19, 37]
Payload
Los datos que se envían en el body de una petición (el JSON de un POST o PUT). En StockFlow se arma con aPayload después de validar. [12, 25, 32]
Preflight
Petición OPTIONS automática que el navegador envía antes de ciertas peticiones entre orígenes (por ejemplo, POST/PUT con JSON) para preguntar si están permitidas. Si falla, la petición real no se envía. [23, 25]
preventDefault()
Método de un evento que cancela el comportamiento por defecto del navegador; en un formulario, evita la recarga de la página al enviarlo. [13]
Preview
npm run preview: sirve localmente la carpeta dist/ para revisar el build antes de publicarlo. No es un servidor de producción. [47]
Promise
Objeto que representa un resultado futuro: queda pendiente, luego se cumple con un valor o se rechaza con un error. fetch y las funciones async devuelven Promises. [22, 31]
Props
Los parámetros que un componente padre le pasa a un hijo. Son de solo lectura para el hijo. Pueden ser datos o funciones (callbacks). [10, 15]
Provider
Componente que pone un valor de Context a disposición de todos sus descendientes (ThemeProvider, ToastProvider). [03]
Q - R
Query params / search params
La parte de la URL después de ? (/productos?categoria=2). Sirven para filtros. React Router los lee y escribe con useSearchParams. [37]
Race condition (condición de carrera)
Error que depende del orden en que terminan operaciones simultáneas: por ejemplo, una respuesta vieja que llega tarde y pisa a una más nueva. Se evita cancelando (AbortController) o etiquetando cada respuesta. [39]
React
Librería para construir interfaces con componentes. Tú describes cómo debe verse la pantalla según el estado y React se encarga de actualizar el DOM cuando el estado cambia. [todas]
React DevTools
Extensión del navegador para inspeccionar el árbol de componentes, sus props, estado y hooks en vivo. [11, 50]
React Router
Librería que asocia URLs con componentes dentro de una SPA (BrowserRouter, Routes, Route, Link, Outlet, useNavigate). [06, 07]
React Testing Library (RTL)
Librería para probar componentes como los usaría una persona: los busca por rol, etiqueta o texto, y comprueba lo que se ve. [43, 44]
Refetch
Volver a pedir los datos al servidor para que la pantalla coincida con él. En StockFlow, reload(). [30]
Regresión
Un error nuevo en algo que antes funcionaba, causado por un cambio. Las pruebas automáticas sirven para detectarlas. [43]
Render / re-render
Cuando React ejecuta un componente para calcular cómo debe verse. Hay un nuevo render cada vez que cambian su estado o sus props. [11, 21]
response.ok
Propiedad del Response de fetch: es true si el status está entre 200 y 299. Hay que revisarla porque fetch no rechaza ante un 404 o un 500. [22]
Route / Routes
<Route path="productos" element={...}> asocia una ruta con un componente; <Routes> elige la que coincide con la URL actual. [06]
Ruta del navegador vs endpoint
La ruta del navegador (/productos) decide qué pantalla se ve y la resuelve React Router. El endpoint (/api/productos) devuelve datos y lo resuelve el backend. [06, 32]
Runtime vs compilación
Compilación: cuando se revisa y transforma el código (ahí actúa TypeScript). Runtime (tiempo de ejecución): cuando el programa corre en el navegador. Los tipos de TS sólo existen en compilación. [04]
S
Secreto
Dato que no debe ser público: contraseñas, tokens, claves privadas. Nunca va en el frontend ni en variables VITE_, porque todo lo del frontend es visible para el usuario. [09]
Service (servicio)
Módulo que agrupa las operaciones HTTP de un recurso con nombres de negocio (productoService.listar, crear…). Es el único que conoce las rutas de ese recurso. [24]
Setter (setState)
La función que devuelve useState para cambiar el estado (setFormData, setPage). Llamarla hace que React agende un nuevo render. Acepta un valor o una función prev => nuevo. [11, 21]
SPA (Single Page Application)
Aplicación de una sola página HTML: la navegación cambia la pantalla con JavaScript sin recargar. StockFlow es una SPA. [01, 07, 48]
Stale closure / datos obsoletos
Cuando una función o Effect sigue usando un valor viejo porque lo "capturó" en un render anterior y no se volvió a ejecutar. Suele deberse a dependencias faltantes. [38]
StrictMode
Modo de React sólo para desarrollo que ejecuta dos veces renders y Effects (setup → cleanup → setup) para revelar errores. No afecta producción. [40]
Suspense
Componente de React que muestra un contenido de espera (fallback) mientras algo se carga, por ejemplo el código de una página lazy. [06]
Swagger / OpenAPI
OpenAPI es la descripción estándar de una API; Swagger UI es la página que la muestra y permite probar endpoints. En StockFlow: http://localhost:8080/swagger-ui.html. Se sirve desde el mismo backend, por eso no tiene problemas de CORS. [23, 32]
T
Toast
Notificación breve que aparece en una esquina y desaparece sola ("Producto creado"). StockFlow la usa para confirmar operaciones y mostrar errores que no pertenecen a un formulario. [18, 25, 28]
TypeError (en fetch)
Error que lanza fetch cuando no hubo respuesta (red, CORS, servidor apagado). StockFlow lo traduce a "No se pudo conectar con el backend". [22, 23]
TypeScript
JavaScript con tipos. Revisa en el editor y al compilar que los datos tengan la forma esperada. En la versión 6 (la de StockFlow) el modo estricto viene activado por defecto. Los tipos se borran al ejecutar. [04, 05]
U - V
UNIQUE
Constraint de la base que impide valores repetidos en una columna (uq_producto_codigo). Resuelve la carrera cuando dos usuarios guardan el mismo código a la vez. [14, 29]
useMemo
Hook que memoriza el resultado de un cálculo y sólo lo repite si cambian sus dependencias. Es una optimización: el código debe ser correcto sin él. [36, 42]
useNavigate / useSearchParams / useLocation
Hooks de React Router: navegar desde código, leer/escribir los parámetros ? de la URL y leer la ubicación actual (incluido el state de navegación). [07, 37]
userEvent
Librería de pruebas que simula interacciones reales de un usuario (clic, escribir, tabular) disparando todos los eventos intermedios. [44]
useState
Hook que crea una variable de estado y su setter: const [page, setPage] = useState(1). [11, 17]
Validación (UI / backend / base)
Comprobar que los datos son correctos. En la UI ayuda al usuario; en el backend es la autoridad; en la base (constraints) es la garantía final. [12, 14]
Variables de entorno
Valores de configuración que se definen fuera del código (archivos .env o el sistema) para cambiar el comportamiento sin editar el programa. [09, 47]
Vite
Herramienta de desarrollo y build para frontend: servidor con HMR en desarrollo y empaquetador optimizado para producción. [02, 47]
VITE_ (prefijo)
Sólo las variables cuyo nombre empieza con VITE_ llegan al código del navegador. Es un filtro de seguridad, pero lo que pasa ese filtro es público. [09]
Vitest
Framework de pruebas que usa la configuración de Vite. Ejecuta los archivos *.test.ts(x) y ofrece describe, it, expect y vi (mocks). [43, 44]
Números de status más usados
200 · 201 · 204
Éxito. 200: OK con datos. 201: recurso creado (trae el objeto y el header Location). 204: hecho, sin contenido (DELETE). [21, 25, 28]
400 · 404 · 409 · 422
Errores del cliente. 400: datos mal formados o inválidos. 404: no existe. 409: choca con datos existentes (duplicado, dependencias). 422: válido en forma pero viola una regla de negocio. [29]
500
Error interno del servidor, no previsto. El usuario no puede corregirlo; la app debe avisar sin fingir éxito. [29, 46]
